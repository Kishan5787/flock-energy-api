# Flock Energy Meter API

A small, production-shaped FastAPI service that places a clean, typed REST boundary in front of the legacy **Urja Meter Ops** portal.

The portal is designed for human browser use and exposes a session-based form login plus a mixture of JSON and server-rendered HTML. This project keeps those legacy details inside an adapter and exposes stable JSON to downstream consumers.

## What is included

- `GET /health` — service liveness.
- `GET /api/v1/meters` — paginated meter listing/search (`q` matches meter ID or serial number).
- `GET /api/v1/meters/{meter_id}` — normalized meter details, hierarchy and coordinates.
- `GET /api/v1/meters/{meter_id}/consumption` — normalized half-hourly consumption readings.
- `/docs` — Swagger UI generated by FastAPI.
- `/openapi.json` — generated OpenAPI contract.
- `PROTOCOL.md` — the observed legacy portal protocol.
- `REFLECTION.md` — engineering reflection and trade-offs.

## Architecture

```text
HTTP consumer
    |
    v
FastAPI routes + Pydantic response models
    |
    v
UrjaPortalClient (anti-corruption adapter)
    |
    +--> session login / automatic re-authentication
    +--> JSON route calls
    +--> HTML parsing + normalization
    |
    v
Urja Meter Ops
```

The route layer owns API semantics and validation. The adapter owns portal authentication, session state, upstream URLs and normalization. This keeps legacy-specific behavior isolated so a future portal replacement does not leak into clients of this API.

## Requirements

- Python 3.10+
- Internet access to the supplied Urja portal
- No paid service is required

## Setup

### 1. Create a virtual environment

```bash
python -m venv .venv
```

Linux/macOS:

```bash
source .venv/bin/activate
```

Windows PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
```

### 2. Install dependencies

```bash
pip install -r requirements.txt
```

### 3. Configure credentials

Copy `.env.example` to `.env` and set the portal credentials supplied with the assignment.

```text
PORTAL_USERNAME=operator@urja.local
PORTAL_PASSWORD=<portal password>
PORTAL_BASE_URL=https://urja-ops.flockenergy.tech
```

`.env` is ignored by Git. Credentials are never hard-coded in application source.

### 4. Run

```bash
uvicorn app.main:app --reload
```

The API will be available at `http://127.0.0.1:8000`.

## Example requests

List the first page:

```bash
curl "http://127.0.0.1:8000/api/v1/meters?page=1"
```

Search by meter ID or serial number:

```bash
curl "http://127.0.0.1:8000/api/v1/meters?q=SE33962&page=1"
```

Get one meter:

```bash
curl "http://127.0.0.1:8000/api/v1/meters/J100000"
```

Get consumption:

```bash
curl "http://127.0.0.1:8000/api/v1/meters/J100000/consumption"
```

Open interactive API documentation at `/docs`.

## Example response

Meter list responses use a stable envelope:

```json
{
  "data": [
    {
      "meter_id": "J100000",
      "serial_number": "SE33962",
      "make": "HPL",
      "phase_type": "single",
      "installation_status": "Decommissioned",
      "transformer_code": "DT-001"
    }
  ],
  "meta": {
    "page": 1,
    "page_size": 20,
    "total": 403,
    "has_next": true
  }
}
```

The `403` value above is an example of the portal state observed during discovery, not a hard-coded application value.

## Error handling

Upstream failures are intentionally not returned as raw portal HTML. The service uses a small structured error envelope:

```json
{
  "error": {
    "code": "UPSTREAM_UNAVAILABLE",
    "message": "The upstream portal did not provide the requested data",
    "request_id": "..."
  }
}
```

A request ID is returned in `X-Request-ID` and is also included in structured API errors.

## Authentication and session handling

The adapter logs in to the legacy portal with its normal form endpoint and keeps the resulting cookie in one `httpx.AsyncClient`. If a request receives `401`/`403` or is redirected back to `/login`, the adapter invalidates the local session, re-authenticates once, and retries the same read operation.

The API consumer never receives or needs the upstream cookie.

## Design decisions and trade-offs

### FastAPI + async httpx

FastAPI gives typed request/response validation and generated OpenAPI with little boilerplate. `httpx.AsyncClient` reuses connections and is a good fit for an I/O-bound upstream integration.

### One process-wide upstream client

This is deliberately sized for the take-home. It gives connection pooling and cookie persistence without introducing a database or distributed session store. A multi-tenant production service should use a credential-scoped session pool instead.

### Pass-through freshness

The API reads current portal data on request rather than silently serving stale cached operational data. A short TTL cache could be added after measuring traffic and acceptable freshness.

### Defensive normalization

The portal uses abbreviated field names, string-encoded numbers and HTML hierarchy data. The adapter converts those into explicit API fields and typed values so downstream callers do not need to understand portal quirks.

### Controlled failure modes

An unavailable upstream is a `502`/`503` style API failure rather than an empty success response. This prevents callers from mistaking an outage for an empty meter set.

## Intentionally left out

The assignment's optional extensions are not required for the core submission, so I intentionally left out:

- a persistent local database/index;
- a separate hierarchy search endpoint;
- a frontend application;
- distributed session storage;
- service-to-service authentication;
- rate limiting;
- write/mutation operations against the portal;
- runtime dependency on scraping frontend JavaScript bundles.

These omissions keep the solution focused on the requested read-only API wrapper and fit the stated 4–6 hour scope.

## Testing

Run:

```bash
pytest -q
```

The tests cover portal-key normalization, HTML hierarchy parsing, credential configuration and consumption parsing with malformed-row handling. The upstream adapter is designed so HTTP interactions can be mocked; real credentials are intentionally not part of CI.

## OpenAPI

FastAPI is the source of truth for the API contract. The checked-in `openapi.json` is generated from the application with:

```bash
python scripts/export_openapi.py
```

For that command, credentials are not required because it only imports the route definitions; an empty configuration is sufficient for schema generation.
